# WeChat 4.1.15.35 (270115), App Store / arm64

## Scope

`config.json` supports silent anti-recall, the native recall notice, and the
custom recall label on Apple Silicon. `Runtime.mm` supports the parser and the
receive-content capture hook for this build. Intel instructions are preserved.
On 2026-10-28, the user reported that anti-recall and the marker worked in their
installed app. This is user-reported live validation; it does not establish every
mode, message type, or one's own recall behavior.

## Parser evidence

The complete arm64 slice has exactly one match for the parser's three-word
prologue plus its `+0x270` guard, `+0xA10` newmsgid store, and four replaceMsg
loads. `LC_FUNCTION_STARTS` bounds the function at `0x4BBAF6C..0x4BBC088`.

| Location | Evidence |
| --- | --- |
| `0x4BBAF6C` | `stp x24,x23,[sp,#-0x40]!; stp x22,x21,[sp,#0x10]; stp x20,x19,[sp,#0x20]` |
| `0x4BBB1D8` | Calls `0x47468F0`, the `revokemsg` comparison helper |
| `0x4BBB1DC` | `40100034`: `cbz w0,0x4BBB3E4`; silent mode uses `82000014`, an unconditional branch to the same destination |
| `0x4BBB97C` | `60E600F9`: `str x0,[x19,#0x1C8]`; notice/custom modes use `7FE600F9`, `str xzr,[x19,#0x1C8]` |
| `0x4BBB1AC`, `0x4BBBA00`, `0x4BBBB78`, `0x4BBBD88` | `ldr x0,[x19,#0x1D0]` |

The wrapper `0x4BBAD58..0x4BBAF6C` copies the input Message's content at `+0x130`
to the handler output's `replaceMsg` at `+0x1D0`. At `0x4BBAEE8`, it calls the
parser with exactly three arguments: output in `x0`, XML string pointer in `x1`,
and an on-stack flag pointer in `x2`. The runtime retains this three-argument ABI.

The parser continuation is `0x4BBAF78`; output offsets are independently decoded
as `newMsgId=0x1C8`, `replaceMsg=0x1D0`.

## Receive-content hook

The finalizer has a unique prefix at `0x4B573B8..0x4B574CC`:

```asm
ldrb w8,[x0,#0x258]
cmp w8,#1
ccmp w1,#0,#0,eq
b.eq 0x4B57430
```

The trampoline replays the first three instructions and continues at
`0x4B573C4`, preserving NZCV for the original conditional branch.

The network constructor at `0x4B5611C` independently establishes the field layout:

- `0x4B56230`: `str x8,[x19,#0xF8]` stores the server ID.
- `0x4B56254`: forms `x19+0x130` before copying message content.
- `0x4B56320`: calls the message-type setter at `0x4B56DB0`; that helper writes
  `w20` to `[x19,#0x0C]` at `0x4B56DE8`.
- `0x4B565D0`: calls the common finalizer after those fields are populated.

## Reserved hook slots

`__DATA` spans `0x9E18000..0xA348000`; its last declared section, `__common`, ends
at `0xA346DB8`. Slots `0xA347F00` and `0xA347F08` are aligned, unclaimed zero-fill
space after that section and before the segment end. They are not file-backed.

| Hook | Entry stub (`adrp x16; ldr x16; br x16`) | Slot |
| --- | --- | --- |
| Parser `0x4BBAF6C` | `70BC02B0108247F900021FD6` | `0xA347F00` |
| Finalizer `0x4B573B8` | `90BF0290108647F900021FD6` | `0xA347F08` |

The runtime locates each slot by decoding the static entry stub after ASLR.

## Mode selection and restoration

`revoke` installs the unconditional guard and restores the original ID store.
`revoke-keeptip` restores the conditional guard and clears the ID. `runtime-tip`
adds both entry stubs, selected together with `revoke-keeptip` in custom mode.

`runtime-tip-reset` restores both original entry prefixes for silent/native
modes. It is excluded in custom mode so it cannot overlap the active stubs.
Every patch accepts its original/replacement counterpart, making mode switches
and repeat application byte-validated. The shared comparison helper is unchanged.

## Validation

- All 21 Swift Testing tests passed, including switching custom → native →
  silent → native → custom without overlapping writes or stale entry stubs.
- A native ARM64 harness compiled the production runtime and reserved a sparse
  synthetic image with this build's exact entry/slot addresses. It installed the
  **actual JSON stubs** and used the real production installer and trampolines.
  Checks passed for both slot writes, the finalizer's EQ/non-EQ branches,
  server ID/type/content capture, a three-argument parser return, clearing another
  sender's recall ID, writing the custom label, restoring one's own recall ID and
  native notice, and leaving unrelated XML extensions unchanged. Both existing
  inline engine self-tests also passed. These are synthetic calls, not real chat.
- A disposable copy of the installed universal app passed CLI dry-run, actual
  patching and `codesign --verify --deep --strict` for custom, repeated custom,
  native, silent, and custom again. For every mode, the complete arm64 `__text`
  exactly matched the baseline with only that profile's declared writes applied;
  x86_64 `__text` was identical to baseline. Post-signing preflight passed.
- The installed app passed read-only custom-mode preflight. No anti-recall
  instructions were changed in the installed app during development.
- After installing and testing the adaptation, the user confirmed on 2026-10-28
  that anti-recall worked and the marker was present. The exact chat scenario and
  full mode/message-type matrix were not reported.

For a new installation, fully quit WeChat, back it up, install the selected
profile with `--config ./config.json`, and reopen it. Have another account send a
new text message and recall it; verify retention and the selected notice. Also
check ordinary text/media messages and one's own recall. Previously recalled
messages are outside the scope of this patch.

The conceptual parser/ID strategy is documented in the upstream
[maintenance notes](https://github.com/fzlzjerry/wechat-antirecall/blob/main/MAINTAINING.md).
No upstream 270115 addresses were reused: addresses and field offsets above were
derived from the installed binary and checked through disassembly.
