# WeChat 4.1.13 (269602) adaptation

## Scope

This entry supports silent anti-recall and an optional native recall notice on Apple Silicon only. It does not claim Intel, auto-update blocking, or multi-instance support for this build. Existing
version entries retain their default `Contents/MacOS/WeChat` target.

## Binary evidence

- Inspected app: `/Applications/WeChat 2.app`, `CFBundleShortVersionString=4.1.13`,
  `CFBundleVersion=269602`.
- Target: `Contents/Resources/wechat.dylib` (universal x86_64/arm64).
- arm64 slice offset: `0xA99C000`; size: `0x9D80150`.
- Original arm64 slice SHA-256:
  `413c124643903640946836d631fb4185133a8ffccbf2863e77b9a4b70568abd6`.
- Revoke parser entry: `0x4941BD4`.
- Patch at `0x4941E44`: `40100034` (`cbz w0, 0x494204c`) becomes
  `82000014` (`b 0x494204c`), retaining the existing branch destination.
- Immediately preceding call at `0x4941E40` targets `0x44DE938`, which constructs
  and compares the `revokemsg` string. The parser's new-message-ID write is
  `str x0, [x19, #0x1c8]` at `0x49425E4`.

The address was located in the installed binary using the parser's guard and
message-ID store, then checked through disassembly and independent build-specific
configuration. Only the parser's conditional branch is changed; the shared
string comparison helper is left intact.

## Validation

Twelve Swift Testing tests passed using the command below, including signing-profile regression tests. They cover original-byte validation, repeat application, dry-run behavior,
paths containing spaces, thin/universal Mach-O files, swapped fat headers, missing
architectures, malformed input, zero-fill regions, multi-file preflight, and symlink escapes. Actual binary
and signing checks use a disposable app copy; the installed app is not modified.

Live message retention still requires a manual test: quit WeChat, back up and
patch the intended app, reopen it, then have another account send and recall a new
message. Confirm the receiving Mac retains it and ordinary messages still work.
Static byte checks and successful signing alone do not establish that behavior.

The local Command Line Tools 6.4 installation requires an explicit testing macro
plugin when using the default Swift build engine:

```bash
swift test --disable-xctest \
  -Xswiftc -load-plugin-library \
  -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing/libTestingMacros.dylib
```

On the disposable 269602 app copy, patching and `codesign --verify --deep --strict`
succeeded. Comparing both architectures' `__text` sections found only the intended
arm64 instruction changed; x86_64 instructions were identical. Post-signing dry-run
recognized the patch despite a changed fat-slice file offset.

## Launch failure and signing correction

The first implementation preserved all original entitlements. Although static
signature verification passed, launching the installed app failed: `amfid`
reported error `-424`, "The file is adhoc signed but contains restricted
entitlements". Static signature integrity is not sufficient to establish launch
compatibility.

`Signing.swift` now reads entitlements through Security.framework, including DER
profiles, and signs nested code before its containing bundles. It removes
`com.apple.developer.*` capabilities that require developer authorization, retaining
App Sandbox, application identity, app groups, microphone, camera, network and file
permissions. It adds per-process library-validation and executable-memory
exceptions needed by the ad-hoc-signed WeChat runtime. Every resulting entitlement
dictionary is checked against the intended profile. Only quarantine xattrs are
removed; unrelated metadata is retained.

The corrected disposable app was launched through Launch Services. Its main,
WeChatAppEx, and helper processes remained running. This validates startup on this
machine; message-retention testing still requires another account to recall a new
message.

- [Apple TN3125: provisioning profiles](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)
- [Community WeChat signing analysis](https://github.com/zengtianli/WeChatTweak/blob/master/Sources/WeChatTweak/Resigner.swift)

## Custom recall label

The custom mode loads `libWeChatTweakRuntime.dylib` from `Contents/Resources` and
hooks the arm64 `parseRevokeXML` entry at `0x4941bd4`. LLDB inspection of this exact
269602 binary confirms the original three-instruction prologue, continuation at
`0x4941be0`, `newMsgId` at `message+0x1c8`, and `replaceMsg` at `message+0x1d0`.
The entry stub points to zero-fill space at `0x9f33f00`, after `__common` and inside
the `__DATA` segment. It calls the original parser, changes the rendered recall line
to `[对方已撤回]`, and preserves the original message. The runtime keeps a sender's
own recall behavior native.

The runtime hook and template renderer are adapted from
[wechat-antirecall](https://github.com/fzlzjerry/wechat-antirecall), distributed
under MIT; its notice is retained in `Sources/WeChatTweakRuntime/LICENSE-MIT`.
This address is verified against the installed 269602 binary but still needs an
end-to-end manual recall test before being considered behaviorally validated.

## Optional recall notice

`--show-recall-notice` selects the separately verified `revoke-keeptip` profile.
It restores the `revokemsg` helper, restores the guarded parser branch and clears
`newmsgid` at `0x49425E4`; this preserves the recalled message while allowing
WeChat to display its own recall notice. Both patch profiles accept each other's
bytes at shared locations, so switching modes is safe and repeatable.

To switch the installed app to the notice mode, fully quit WeChat, then run:

```bash
sudo .build/debug/wechattweak patch \
  --app "/Applications/WeChat 2.app" \
  --config ./config.json \
  --show-recall-notice
```

Omit `--show-recall-notice` to return to silent mode. The alternate behavior is
byte-validated against the exact installed 269602 arm64 binary; test it with a
new recalled message before relying on its display behavior.
